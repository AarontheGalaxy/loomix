# Voicemeeter Potato manual, pages 106-112

## VAIO Extension Activation Code, restated (p.106)

- **Same mechanism as p.101** (p.106): a separate purchasable license
  (own Challenge/Response pair) enabling VAIO routing for stereo input
  strips 1-5 and physical buses A1, A2, A3, A4, A5. Same webshop/
  activation flow as the main Potato license (pp.102-105); its own
  license slot appears separately in the webshop "My License" page, with
  its own independent Regen option. Recommends storing a computer
  footprint (p.100) before a clean Windows reinstall so this license can
  be recovered too. No new mechanism beyond what pp.99-105 already
  covered — pure repetition for this specific license type.

## Known issues / recommendations (pp.107-108)

Real documented product *behaviors*, not bugs, presented as
troubleshooting guidance — worth capturing since several describe actual
mixer/engine semantics:

- **Exclusive output access** (p.107): once Voicemeeter is running and a
  device is selected as one of its outputs (A1, A2, A3...), Voicemeeter
  gets exclusive access to that device, preventing other applications
  from also using it — by design, the same way a physical mixing
  console's amp input has exactly one thing connected to it.
- **No sound if not running** (p.107): if Voicemeeter's own virtual
  device is set as the *system* default device, Voicemeeter itself must
  be running for sound to work at all (analogous to a mixing console
  needing to be powered on).
- **Passive when unused** (p.107): Voicemeeter's application and virtual
  drivers do nothing on their own if not actually selected/connected
  anywhere — they can't corrupt or disturb the system; "no sound" is
  always traceable to an audio *configuration* issue (default playback/
  recording device in Windows, or an app like Zoom/Discord/Spotify/OBS
  still pointing at the wrong device).
- **Outputs are not sample-accurately synchronized across devices**
  (p.107): every physical I/O point runs independently; when a bus's
  outputs are spread across several different audio *devices*, there can
  be audible drift/echo between them (each device runs its own clock).
  This is called out as expected, physically-constrained behavior, not a
  bug — correctable via the per-bus **Monitoring Synchro Delay** fields
  in System Settings (a manual compensating delay line per bus, 0.00ms
  shown by default for every bus in the example screenshot).
- **Engine requires output A1's device to be running** (p.108): the
  audio engine only runs if output A1's selected device is actually
  running — *unless* no device at all is selected for A1, which puts
  Voicemeeter on its internal clock (for a PC with no output device
  available at all).
- **Audio Stream can stop entirely (no sound, no meter movement)**
  (p.107): can happen when Windows' own audio configuration changes, or
  a USB device is plugged/unplugged while Voicemeeter is running. Fix:
  restart the audio engine, or simply re-select an audio device on
  output A1 or any input — this auto-restarts the stream (if that
  doesn't help, another process has likely taken exclusive ownership of
  the device).
- **Choppy/crackling/discontinuous audio** (p.108): generally means the
  current audio interface/buffer-size combination isn't actually stable
  on this system — try a different interface type or larger buffer.
  Specific note: Discord reportedly won't work correctly at any sample
  rate other than 48kHz, so a Voicemeeter virtual output used as
  Discord's input device should be explicitly set to 48kHz in Windows'
  own device properties (screenshot shows the exact Windows Sound
  "Recording" tab / device "Advanced" tab dialog and its sample-rate
  dropdown, several rates listed 8kHz-192kHz at 16/24-bit).
- **Windows Update can disturb audio** (p.108): a Win10/11 update can
  silently change default-device settings or privacy rules — named
  example: microphone privacy settings blocking Voicemeeter's recording
  access; Windows 11's power-throttling feature can also destabilize the
  audio stream specifically when the Voicemeeter window is minimized.

## VB-Audio Device Checker (pp.109-110)

- **VBDeviceCheck.exe** (p.109): still listed in the Voicemeeter menu but
  no longer auto-run on startup (as it was with the previous driver
  generation); originally built to detect a Windows-update-triggered
  driver reinstallation issue (checking icon/pin-name/driver-version
  fields expected to stay constant) — now largely superseded since
  VAIOs/VB-CABLEs are expected to self-update for Win10+.
- **Diagnostic output** (p.109): a text log checking every known
  VB-Audio virtual device (Virtual Cable, Cable A-D, MT128, Hi-Fi
  Cable, Voicemeeter VAIO, AUX VAIO, VAIO3), each reported Installed/
  Not Installed with version info, ending in an overall "CONCLUSION: OK
  (nothing bad detected)"-style summary.
- **Driver consolidation note** (p.109): on Windows 10+, the 3 separate
  legacy VoiceMeeter drivers are no longer installed individually — a
  single "Voicemeeter VAIO" driver with 8 I/O replaces them, simplifying
  maintenance; the checker's "not installed" warnings for those legacy
  names are expected and can be ignored.
- **Audio Device List** (p.109-110): the same Device Checker app can
  also list every VB-Audio virtual device (playback and recording sides)
  exactly as the Windows Sound dialog would, showing each one's current
  audio format (the "MIX Format") and exclusive-mode properties (not
  always populated correctly, per the manual's own caveat).

## Where settings files are stored (p.110)

- **Settings location** (p.110): every Voicemeeter edition's and Macro
  Buttons' current settings are stored as XML files under `My
  Documents\Voicemeeter`.
- **Today/Yesterday dual-copy mechanism** (p.110): for Macro Buttons and
  every Voicemeeter edition, the config-file manager keeps *two* rolling
  copies of the settings — a "Today" file (the configuration state as of
  the start of the current day) and a "Yesterday" file (the configuration
  that was in use the day before) — visible in the folder listing as
  `Voicemeeter<Edition>_TodaySettings.xml` /
  `..._YesterdaySettings.xml` / `..._LastSettings.xml`, alongside the
  Preset Scene files (`Scene_Standard`/`Scene_Banana`/`Scene_Potato`) and
  VAIO-extension activation logs.

## Command-line installation (p.111)

- **Silent install/uninstall flags** (p.111): `-h` (hide GUI), `-i`
  (install), `-u` (uninstall) — passed to the setup program; a reboot is
  still required after each operation, so the recommended sequence for
  an update is: uninstall the previous version, reboot, install the new
  one, reboot again.

## Voicemeeter command line (p.111)

- **Restart Audio Engine via shortcut** (p.111): `Voicemeeter.exe -R`
  (or `-r`) — useful for a desktop shortcut that re-activates a USB
  headset that was already selected as a Voicemeeter hardware input but
  wasn't physically plugged in at the time Voicemeeter started; simply
  restarting the engine after plugging it back in makes it work again
  without restarting Voicemeeter itself.
- **Launch with a specific config file** (p.111): `-l"filename.xml"` or
  `-L"filename.xml"` (only takes effect if Voicemeeter isn't already
  running — a no-op otherwise); accepts a bare filename (same directory
  as the executable), a relative subfolder path, or a full absolute
  path.

## Registry parameters (p.112)

Under `HKEY_CURRENT_USER\VB-Audio\VoiceMeeter`; the manual explicitly
warns not to modify undocumented values without support guidance, and
that only the ones named here are meant to be user-tunable:

- **`DelayedStartS`** (p.112): countdown, in seconds, before the audio
  engine starts on launch (default 5) — shown as a growing countdown bar
  over the device-selection area, to give every audio service/driver
  time to finish starting before Voicemeeter's own engine starts (a
  driver not ready in time won't work until the engine is restarted
  manually).
- **`preferredResolution`** (p.112): preferred bit resolution for Banana/
  Potato (default 24-bit); Standard always uses 16-bit with the Windows
  Audio Interface. The actual final resolution is still a negotiation
  with the audio interface, which can force a different value.
- **`MaxMonDelayMS`** (p.112): default 500ms; the ceiling for the
  per-bus monitoring-delay fields in System Settings; redefinable from
  500ms up to 5000ms (5 seconds max) via this registry key.
- **`PreRecordingTimeMax`** (p.112): 10 to 60 seconds (default 20);
  sizes the pre-recording rolling-buffer memory allocation at startup
  (example given: ~90MB for 60 seconds at 48kHz).
- **`TimerResolution`** (p.112): defaults to `1` (forces the system
  timer resolution to 1ms); set to `0` to use the coarser 0.5ms
  [likely a units inconsistency in the source: elsewhere 1ms is finer
  than 0.5ms, so this may mean the reverse — transcribed exactly as
  printed, not corrected] system timer resolution instead.
- **`AutoUpMixMode`** (p.112): if set to `1`, an up-mix bus mode
  auto-detects whether the incoming signal is genuinely stereo or
  already multichannel, by checking for material above **-80 dBFS on
  channels 3, 4, 5...** — if found, the signal is treated as already
  multichannel and the Up Mix transform is *not* applied. This is the
  exact mechanism (and exact threshold, -80dBFS, and exact channels
  checked, 3/4/5) behind the "optional refinement" a previous review
  pass flagged as missing from `docs/SPEC.md`'s bus-mode section —
  confirmed here precisely, from the primary source, not inferred.
- **`EngineMode`** (p.112, "AUDIO EXPERT/DEVELOPERS" only): a bit field
  of WASAPI-engine-related features, must be `0` by default — "these
  historic modes are not tested anymore in our dev cycle." Bit values:
  `0x00000001` = `MODE_SWIFT`; `0x00000100` = `INPUT_EXCLUSIVE_MODE`;
  `0x00000200` = `OUTPUT_EXCLUSIVE_MODE` (annotated "set anyway in
  Voicemeeter" in the source, i.e. output exclusive mode is applied
  regardless of this flag through some other path). Directly confirms
  pp.90 and 92's "Swift mode / WDM exclusive input mode have been
  disabled" — these are the literal bit flags for those now-untested,
  effectively-deprecated modes.
